# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`dbman` is a vim-like terminal UI (TUI) database browser built with [Textual](https://textual.textualize.io/). It connects to SQLite (primary target) and in theory PostgreSQL/MySQL via SQLAlchemy Core, to a CouchDB database via its HTTP API, or to the databases living on a Notion page via the Notion API, letting you browse tables/views (or documents/design-doc views, or Notion databases), edit cells, run ad-hoc SQL (or JS map/reduce views), and — for relational backends — view a force-directed ER diagram of foreign-key relationships, all from the terminal.

## Running

```bash
./dbman <path-to-sqlite-file-or-db-url>          # e.g. ./dbman garden.sqlite
./dbman couchdb://user:pass@host:5984/dbname     # CouchDB, one database per invocation
./dbman notion://<integration-token>@notion.so/<page-id>  # Notion, one page's child databases per invocation
./dbman                                          # bare: reconnect to the last-used connection saved in ./dbman.json
./dbman <saved-connection-name>                  # reconnect to a specific saved connection by name
./dbman notion://<token>@notion.so/<page-id> --name notion  # save this connection under a friendly name
```

`./dbman` is a wrapper script that invokes `venv/bin/python3 dbman.py "$@"`, so it always runs inside the project's own virtualenv regardless of the caller's shell environment. Prefer running through this wrapper rather than `python3 dbman.py` directly, or make sure the venv is activated first.

Every successful connect auto-saves into `./dbman.json` (see "Workspace" below), so once you've run `./dbman garden.sqlite` once from a project directory, a bare `./dbman` from that same directory reconnects to it and restores where you left off.

Connection string dispatch happens in `providers/__init__.py:create_provider()`: a `couchdb://`/`couchdbs://` URL selects `CouchDBProvider`, a `notion://` URL selects `NotionProvider`; anything else that doesn't already start with `sqlite://`, `postgresql://`, or `mysql://` is treated as a filesystem path and turned into a `sqlite:///<abspath>` URL, then handed to `SqlAlchemyProvider`.

Dependencies (`requirements.txt`): `textual`, `sqlalchemy`, `requests`. Install into the venv with `venv/bin/pip install -r requirements.txt`. `requests` is only imported lazily inside `providers/couchdb_provider.py` and `providers/notion_provider.py` (each only imported when its URL scheme is used), so a SQL-only environment never needs it at import time.

## Tests

There is no test runner configured (pytest is not installed in `venv`). `test_layout.py`, `test_lines.py`, and `test_ortho.py` are standalone algorithm prototypes (force-directed graph layout, Bresenham line drawing, orthogonal line routing) with no assertions — they just `print()` output for manual inspection. Run them individually with `venv/bin/python3 test_layout.py` etc. when iterating on diagram-rendering math in isolation before porting the logic into `DiagramView` in `dbman.py`.

There's also no automated coverage of the app itself — verify changes by actually running `./dbman` against `garden.sqlite` (and, for provider-layer changes, against a local CouchDB — see "Testing the CouchDB provider" below — or a real Notion page — see "Testing the Notion provider" below).

## Architecture

`dbman.py` is the Textual `App` — UI only (sidebar, modals, keybindings, `DataTable`/diagram rendering). All backend-specific logic (SQLAlchemy Core, CouchDB's HTTP API) lives behind a **provider abstraction** in `providers/`, so the UI never touches SQLAlchemy or `requests` directly. `plugins/lookup.py` is the one plugin. There's no build step.

### Provider abstraction (`providers/`)
- `providers/base.py` defines the `Provider` ABC plus its data shapes: `Column` (including `read_only`, `True` for computed/system columns like Notion's formula/rollup/created_time — `action_edit_cell` now refuses these up front, since it has the `Column` in hand via `DbMan.columns_by_name`, rather than round-tripping to the provider just to get its `ValueError` back through the `self.notify(..., severity="error")` path; and `options`/`multi_value`, the enum-like column contract — a non-empty `options` tuple of `ColumnOption(name, color)` means the UI offers a picker instead of a free-text box, for both editing and filtering, and `multi_value` says a cell holds several options at once. Only `NotionProvider` populates these today, from a `select`/`status`/`multi_select` property's declared option set), `RowKey` (an opaque per-row identity — an int rowid for SQLite, `{"_id", "_rev"}` for CouchDB, a page id for Notion), `RowPage` (columns + rows + row_keys + pagination cursor/`has_more`, plus optional `raw_rows` for whole-document editing), and `Capabilities` (per-provider feature flags: `diagram`, `lookup_plugin`, `truncate_column`, `whole_row_edit`, `open_in_browser`, `create_definition`, `delete_item`, `add_row`, `delete_row`, `reorder_row`). `DbMan` reads `self.provider.capabilities.*` before wiring up diagram mode, the lookup plugin, truncate, whole-document edit, view create/edit, and delete — this is how the UI degrades gracefully per backend instead of crashing on `NotImplementedError`.
- `providers/__init__.py`'s `create_provider(db_url)` is the only dispatch point. **To add a new provider**: implement `Provider`, set `capabilities` honestly, add one `elif` branch here. There's deliberately no plugin registry/discovery — this one-`elif` extension point is intentional, not a stopgap.
- `providers/sqlalchemy_provider.py` (`SqlAlchemyProvider`) is the relational-DB implementation — see below.
- `providers/couchdb_provider.py` (`CouchDBProvider`) is the CouchDB implementation — see below.
- `providers/notion_provider.py` (`NotionProvider`) is the Notion implementation — see below.

### `SqlAlchemyProvider` (relational: SQLite primarily, Postgres/MySQL best-effort)
- A single SQLAlchemy `engine` is created once and shared for the provider's lifetime. There is no ORM layer — all queries go through SQLAlchemy Core (`MetaData()`/`Table(..., autoload_with=engine)`, `select()`, `update()`, `text()`), and tables/columns are *reflected live* on every read rather than cached, so schema changes made through the app (or externally) show up immediately.
- SQLite-specific behavior is special-cased throughout (`self.engine.dialect.name == "sqlite"`): rowid-based editing (`WHERE rowid = :rid`), `sqlite_master` for raw `CREATE` SQL, `ON CONFLICT DO UPDATE` upserts (in `LookupPlugin`). Postgres/MySQL paths exist but are noticeably thinner (no PK-based UPDATE fallback is implemented yet — see the `# PK logic needed for non-sqlite` comment in `update_cell`) — don't assume feature parity across dialects.
- Paging (`get_page`) is real offset-based paging: it fetches `page_size + 1` rows to detect `has_more` without a separate `COUNT(*)`, and `cursor` is just `str(offset)`.
- dbman stores its own metadata *inside the target database*, in tables prefixed `_dbman_` (`_dbman_layout` for diagram node positions, written directly by `DiagramView` via `provider.sqlalchemy_engine()`; `_dbman_lookup_config` for FK lookup display-column config, owned by `plugins/lookup.py`). These are filtered out of the sidebar/table lists everywhere alongside `sqlite_*` internal tables.
- `capabilities`: everything is `True` (diagram, lookup_plugin, truncate_column, create_definition, delete_item) except `whole_row_edit` (rows are flat/typed, not JSON documents, so there's no "edit whole row as JSON" concept here) and `add_row`/`delete_row` (not implemented for this provider yet — `add_row` needs a schema-aware form for `NOT NULL` columns without defaults, deferred to a future dynamic-forms layer; `delete_row` is a plain `DELETE FROM ... WHERE rowid = ...`, straightforward but not yet wired up).

### `CouchDBProvider` (document DB)
- **Concept mapping**: a `couchdb://` URL names exactly *one* CouchDB database (consistent with "one DB per dbman invocation"). That database itself is dbman's single sidebar "table" entry (all documents, browsed via Mango `_find`); each design-doc map/reduce view is a sidebar "view" entry named `"ddoc/view"`.
- **Schema is inferred, not declared**: `get_schema`/`get_page` sample up to 200 documents and infer a flat column set (union of top-level keys, `_id`/`_rev` first, ranked by frequency, capped at 15 columns) with a per-field type guess (`"mixed"` if a field's type varies across sampled docs). Nested (`dict`/`list`) values are stored as their raw Python object in the `DataTable` cell (not stringified) so `action_edit_cell` can detect them.
- **Paging** deliberately avoids `_all_docs?skip=N` (skip-based paging is O(skip) in CouchDB). Documents use Mango `_find`'s `bookmark` cursor; design-doc views use `startkey`/`startkey_docid` — but since those bounds are *inclusive*, a cursored view page re-fetches and drops one duplicate leading row (see the `skip_duplicate` handling in `_get_view_page`).
- **Editing**: `update_cell`/`update_row_json` always re-`GET` the document immediately before `PUT` to get the freshest `_rev`, rather than trusting a value captured at page-load time — this isn't full optimistic-concurrency conflict handling (a genuine race can still 409), but it's a deliberate, low-effort match to the SQL path's equally non-transactional update-by-rowid risk posture. `E` (`action_edit_document` in `dbman.py`) opens the *whole* document as JSON (seeded from `RowPage.raw_rows`, so fields outside the inferred column set are editable/addable); plain `e` on a `dict`/`list`-valued cell auto-routes to the same whole-document editor instead of the single-line `EditCellScreen`.
- **View create/edit** reuses the same `EditTextScreen` modal as SQL's "Create View"/"Edit SQL", but with a plain-text template format (`DESIGN_DOC:` / `VIEW_NAME:` / `MAP:` / `REDUCE:`) parsed by `_parse_view_definition` and written as a design-doc via `_put_design_view` — there's no real "SQL" here, just a text format chosen to fit the existing modal.
- **Adding rows** (`a` on a Table → `DbMan._add_row()`, `capabilities.add_row`): CouchDB has no fixed schema, so `provider.add_row()` just `POST`s an empty `{}` document and lets CouchDB assign the `_id` — `dbman.py` immediately opens the fresh (empty) document in the same whole-document JSON editor as `E`/`action_edit_document` (`_open_document_editor`, shared by both), since a freeform add is meant to be filled in right away. `SqlAlchemyProvider` doesn't implement this (`capabilities.add_row` stays `False`): a table's `NOT NULL` columns without defaults need a schema-aware form, deferred to a future dynamic-forms/business-logic layer rather than guessed at here. `a` is provider-agnostic and polymorphic beyond just this: on a View (any provider with `capabilities.create_definition`) it dispatches to `DbMan._add_view()` instead — the same "create new view" flow formerly bound to a standalone `v` key, folded into `a` since it's the same "add a new thing" gesture, just for a different item type. See `_add_ctx` and `DbMan.action_add`.
- **Capabilities that are permanently off** (not "not implemented yet", but conceptually N/A and gated in `dbman.py`'s action methods): `diagram` (no FK-equivalent — `DiagramView` shows "Diagram not available for this provider" and `m` mode-cycling skips diagram entirely), `lookup_plugin` (FK-lookup is inherently relational), `truncate_column` (no sane "bulk-mutate one field across heterogeneous docs" semantics), `delete_item` (the one "table" entry *is* the whole database — deleting it is out of scope for a cell-level browser).
- **Future CouchDB-specific persisted state** (if a diagram-equivalent or similar feature is ever added for CouchDB) should follow the same pattern as `_dbman_layout`/`_dbman_lookup_config`: a sibling `_dbman_meta` CouchDB database, with docids scoped `"<source-db>:<namespace>"` to avoid collisions across multiple dbman-browsed databases on the same server. This isn't implemented — it's the documented convention to follow when it's needed.

### `NotionProvider` (Notion databases-as-tables) — see issue #16

- **Concept mapping**: a `notion://<integration-token>@notion.so/<page-id>` URL names exactly one Notion page (auth token embedded in the URL, gitignored in `dbman.json`, matching CouchDB's convention). The page id deliberately lives in the URL *path*, not the host, mirroring CouchDB's `couchdb://user:pass@host/dbname` shape — `derive_db_name()` (`view_settings.py`) extracts a connection name from the path, and a host-only shape would leave the path empty and fall back to hashing the whole URL (token included) into the saved connection name and a `.dbman/*.json` filename on disk. The host segment itself (`notion.so` above) is a readable placeholder — the provider never actually connects to it, every request goes to `api.notion.com`. Each `child_database` block that lives directly under that page becomes one dbman "table" — confirmed against a real page that this works for both inline and full-page-view child databases. There is no separate "view" concept yet (`list_views()` always returns `[]`); a database row is a Notion page (`RowKey` = page id).
- **Schema is declared, not inferred** (unlike CouchDB): `get_schema` reads `GET /databases/{id}`'s `properties` map directly — one HTTP call, no document sampling. Pinned to `Notion-Version: 2022-06-28` deliberately, since Notion's newer multi-data-source database model (2025-09-03+) would require picking a data source per database; out of scope until a database on a real workspace actually needs it.
- **Editable vs. read-only columns**: `_EDITABLE_TYPES` in `notion_provider.py` covers the flat scalar property types (`title`, `rich_text`, `number`, `checkbox`, `url`, `email`, `phone_number`, `date`) plus the three enum-like ones (`select`, `status`, `multi_select`). Everything else (`relation`, `people`, `files`, `formula`, `rollup`, `created_time`/`last_edited_time`/`created_by`/`last_edited_by`, `unique_id`, and any unrecognized type) is flattened to a display string by `_read_property` but marked `Column.read_only = True`; `_write_property` raises for these too, so a write that slips past the UI's own read-only guard still surfaces as a normal `"Update failed: ..."` notification rather than crashing.
- **Enum-like properties are picked, never typed** (`_CHOICE_TYPES` = `select`/`status`/`multi_select`): `get_schema` surfaces each property's declared option set — name *and* color — as `Column.options`, read straight out of the `GET /databases/{id}` response it already makes, so it costs no extra round trip. This is a correctness fix before an ergonomic one: writing an arbitrary name to a `select` or `multi_select` *silently creates a new option* on the user's real database, while the same on a `status` 400s (Notion's API can't create status options at all). Picking from the declared set can do neither, which is why `status`/`multi_select` only became writable once the picker existed. `select`/`status` use `ChoiceSelectScreen` (a `Select`, plus a `(none)` entry that clears the property); `multi_select` uses `MultiChoiceScreen` (a `SelectionList`, dismissing a real `list[str]` — `_write_property`'s string fallback via `_split_multi` exists only for a value that came back out of a cell, and can't round-trip an option name containing ", ").
- **Paging** is a direct fit, unlike SQL's offset-simulation or CouchDB's bookmark/skip-duplicate dance: Notion's `POST /databases/{id}/query` is natively cursor-based (`start_cursor` in, `next_cursor`/`has_more` out), passed straight through to `RowPage`.
- **Filtering** is per-property-*type* (the condition nests under a key named after the type), unlike the one-clause-fits-every-column shape the other two providers enjoy. `_build_notion_filter` handles both value shapes from `get_page`'s contract: a `list` (a picker selection on an enum-like column) becomes an `or` of exact conditions via `_notion_choice_condition` — `equals` for `select`/`status`, `contains` for `multi_select`, plus the `FILTER_EMPTY`/`FILTER_NOT_EMPTY` sentinels — and a `str` goes through `_notion_filter_condition` as before. Several filtered columns compose as an `and` of those, i.e. two levels, which is exactly the 2022-06-28 compound-filter API's maximum nesting depth; don't nest further.
- **`*` wildcards are text-only** (`_wildcard_filters`, shared by `_build_notion_filter` and `get_page` so the two can't disagree about which entries the server is handling). A filter value containing `*` on a `_TEXT_FILTER_TYPES` column is routed around the server-side filter and matched client-side with `fnmatch` against the row's already-flattened display value, because Notion's text `contains` is a plain substring with no prefix/suffix anchoring. That's the whole justification, and it doesn't extend to enum-like columns: those are picked from a dropdown now, so a glob there is neither producible from the UI nor meaningful against an exact-`equals` API. (Wildcards were originally added blanket-wide precisely *because* typing into a `select` filter box 400'd — the picker addresses that cause directly, and the glob stayed only where it earns its keep.) Client-side matching happens after the page is fetched, so `has_more`/`next_cursor` still reflect Notion's unfiltered pagination: a page can come back with fewer rows than `page_size`, but paging forward still converges on every match.
- **Editing**: `update_cell` re-fetches the database's property-type map before writing (properties can be renamed/retyped in Notion independently of dbman), then `PATCH /pages/{id}` with a type-wrapped property value — no revision/optimistic-concurrency handling, same non-transactional risk posture as the SQL and CouchDB paths.
- **Adding rows** (`capabilities.add_row = True`): `POST /pages` under the target database with just the title property set to empty, mirroring CouchDB's "create minimal, then fill in via cell edits" posture — but since Notion properties are typed (unlike CouchDB's freeform JSON), there's no whole-document JSON editor step; the new row's cells are edited in place like any other row.
- **Row editing hands off to Notion itself rather than an in-app modal** (`capabilities.open_in_browser = True`, `whole_row_edit` stays `False`): a Notion database row is a full Notion *page* — properties plus a rich block-content body (paragraphs, headings, lists, embeds, ...) that dbman has no representation for and isn't attempting to build one for (a body-content round-trip was considered and explicitly deferred — the archive-then-reappend semantics Notion's API would require for replacing a page's children aren't atomic, and a faithful bidirectional block/Markdown converter is a project of its own). Instead, `get_row_url` returns that row's own canonical share link (a bare no-dash `https://www.notion.so/<page-id>` — verified this resolves with no title slug needed) and `action_open_in_browser` (`dbman.py`) just `webbrowser.open()`s it, handing the whole row off to the Notion desktop app (if installed and registered for `notion.so` links) or the web app in a browser — dbman never sees or edits body content at all. Property-cell edits made there won't auto-refresh in dbman's table; same "reload to see external changes" posture as every other provider.
- **Row deletion archives, matching Notion's own "Delete" button** (`capabilities.delete_row = True`): Notion's API has no permanent-delete for pages, so `delete_row` `PATCH`es `{"archived": true}` — the same operation Notion's own UI performs (moves it to Trash, recoverable there), not a workaround. This is a genuinely new, distinct capability from `delete_item` (table/view granularity, see below) — bare `d` in `dbman.py` is polymorphic the same way `e` is: in View mode with the `DataTable` focused in row-select mode, it deletes the selected row (`_delete_row`, gated on `delete_row`) instead of the whole table/view (`action_delete_item`'s existing sidebar/current-item path, gated on `delete_item`). See `_delete_item_ctx`.
- **Persistent row reordering** (`capabilities.reorder_row = True`, `Provider.reorder_rows`): Notion's query API has no native manual-order concept, so dbman owns a dedicated `_dbman_order` number property on the database — lazily added and backfilled with spaced values (1000, 2000, ...) the first time a reorder is attempted (`_ensure_order_property`/`_backfill_order`), then always sorted ascending in `get_page` once present. It's filtered out of `get_schema`'s returned columns, so it's invisible in View/Schema/SQL mode alike — a real, visible Notion property under the hood (unlike `_dbman_layout`'s sidecar-table trick for SQLite, there's no join/sidecar concept in Notion's API to tuck it away in). `reorder_rows` reassigns the touched rows' *already-known* order values among themselves (a pure permutation, read via point `GET /pages/{id}` calls) rather than deriving each row's position from a live query mid-batch — see the UI structure section's optimistic-local-move pattern below for why: an earlier design that issued one query-based swap per keystroke broke under a fast burst, because Notion's `POST /databases/{id}/query` index measurably lagged behind its own very recent writes (a couple of seconds, observed against a real page) — a second move in the same burst could still see pre-first-move ordering. Point GETs on `/pages/{id}` showed no such lag.
- **Capabilities that are off for now** (`diagram`, `lookup_plugin`, `create_definition`, `truncate_column`, `delete_item`): `diagram`/`lookup_plugin` are plausible fast-follows since Notion's `relation` property type is a genuine FK equivalent (see issue #16) but aren't wired up yet; `delete_item` operates at table/view granularity everywhere else in dbman (see `SqlAlchemyProvider.delete_item` dropping a whole table) — archiving/deleting a whole Notion *database* is a much bigger hammer than the row-level `delete_row` above and isn't exposed from dbman.
- **Database discovery** (`_discover_databases`) only finds databases actually owned by the page's own block tree (`GET /blocks/{page_id}/children`, paginated, filtered to `type == "child_database"`); a "linked database view" whose true parent page is elsewhere in the workspace won't be found this way — a known, documented limitation, not a bug.

### UI structure (`DbMan(App)`)
- Layout: a sidebar `ListView` (Views / Tables / Plugins sections) + a `ContentSwitcher` that swaps between three widgets: `#data-table` (a `DataTable`), `#sql-view` (a `Static` showing the item's "definition" — raw `CREATE` SQL, or a CouchDB view's map/reduce source), and `#diagram-view` (`DiagramView`).
- `self.mode` is one of `"view" | "schema" | "sql" | "diagram"`, cycled with `m` (skipping `"diagram"` if `provider.capabilities.diagram` is `False`). There's no direct-jump-to-diagram key — `ctrl+d`/`command+d` formerly did this but were reclaimed (`ctrl+d`/`ctrl+u` now alias `pageup`/`pagedown`'s screen-scroll, the vim convention — see the paging note below) since `command+d` is unreliable in most terminal emulators (commonly intercepted as "split pane"), leaving `m`-cycling as the only path to diagram mode. `load_item()` is the central dispatcher that reads `self.mode` + the selected sidebar item's type (`"table" | "view" | "plugin"`) and populates the right widget via `self.provider.*` calls. Bare `d` is `delete_item`/row-delete instead (issue #10 follow-up; see `_delete_item_ctx` for the row-vs-whole-item polymorphism) — `m`-cycling plus per-object direct-jump/edit keys is expected to eventually replace `self.mode` entirely (see the open design note for a `table/edit`, `view/edit`, `column/edit`, `database/edit` object+action vocabulary), but that's not implemented yet.
- Row identity for editing flows through `self.row_keys: dict[str, RowKey]` (DataTable string row-key → the provider's `RowKey`, rebuilt on every `load_item`) and `self.raw_docs: dict[str, Any]` (same keying, populated only when `RowPage.raw_rows` is present — i.e. only for CouchDB's document table, feeding whole-document edits).
- View-mode paging state (`self.page_cursor`, `self.page_history` as a back-stack, `self.page_size`, `self.page_has_more`) is reset whenever the selected sidebar item or `self.filters` changes (see `reset_paging()`); `]`/`[` step forward/back (a real DB refetch of the next/previous `page_size`-row chunk) and the title bar shows a `[page N+]` indicator when more rows exist — distinct from `pageup`/`pagedown` (and the hidden secondary `ctrl+d`/`ctrl+u`), which just scroll the cursor by one screenful within the currently loaded chunk via the DataTable's own paging, matching vim's ctrl+d/ctrl+u convention. These two "page" concepts were briefly conflated (`ctrl+d`/`ctrl+u` aliased to `next_page`/`prev_page` instead) until real-world testing against an ~800-row CouchDB table showed the DB-chunk semantics (fixed `page_size = 500`, unrelated to viewport height) tripped "no more rows"/"already at first page" after a single press — not what vim users expect from ctrl+d/ctrl+u.
- `self.select_mode` is one of `"field" | "row" | "column"` (View mode only), rotated with `s` (`action_rotate_select_mode`, silently — no popup, since the title bar's `[ROW]`/`[COLUMN]` suffix is the intended feedback) and mapped 1:1 onto Textual `DataTable`'s native `cursor_type` reactive (`"cell" | "row" | "column"`) via `DbMan.CURSOR_TYPE_BY_SELECT_MODE` — row/column highlighting and cursor movement semantics come from Textual for free. `load_item()` re-applies `cursor_type` after every rebuild (resetting to `"cell"` outside View mode); the title bar shows a `[ROW]`/`[COLUMN]` suffix via `update_title()`. It determines what `e` (`action_edit_cell`, footer label just "Edit" since what it edits varies) operates on: field mode edits the focused cell (unchanged); row mode routes to `action_edit_document` if `provider.capabilities.whole_row_edit`, else to `action_open_in_browser` if `provider.capabilities.open_in_browser` (Notion — see above), else notifies it's unsupported — switch to field mode; column mode currently has no `e` action (`t`/truncate and `H`/`L` already act at column granularity). In column mode, `H`/`L` (`action_reorder_column`) swap the selected column with its neighbor and persist the new order to `ViewSettingsStore` (`settings.order`), superseding the earlier grab/drop design (issue #4). `H`/`L` deliberately reuse the app's own `h`/`l` = left/right cursor-movement mnemonic (shift = "move the column instead of the cursor"), which was settled on after two dead ends: `ctrl+left`/`ctrl+right` was avoided since macOS reserves those for Mission Control space-switching; `alt+left`/`alt+right` (still bound as a hidden secondary, `show=False`) is unreliable since macOS terminals commonly send Option+Left/Right as the readline word-jump escape sequence rather than the xterm modified-arrow CSI sequence Textual needs to recognize `alt+left`/`alt+right`, so it silently never fired for most users; and `<`/`>` (tried next) required Shift+,/Shift+., which turned out to be easy to mis-key by visually identifying the unshifted comma/period glyphs instead of reaching for Shift. See issue #7.
- All interactive dialogs (edit cell, edit whole document, pick option / pick options, filter, confirm delete, truncate column, edit text [SQL or CouchDB view JS/JSON], export CSV, lookup select) are `ModalScreen` subclasses pushed with `self.push_screen(Screen(...), callback)` — the callback receives the dismissed value. Follow this pattern for new modal interactions rather than inlining prompts.
- `self.columns_by_name` (name → provider `Column`, rebuilt alongside `self.column_widths` in `load_item`'s View branch and cleared in the others) is what lets the column-scoped actions see a column's `options`/`multi_value`/`read_only`. The `DataTable` only carries column *name* strings, and re-reading the schema is a network call for Notion, so anything needing column metadata per keystroke reads it from here rather than calling `provider.get_schema`.
- `self.filters` is `{column_name: str | list[str]}` — a union rather than a richer object, deliberately, so every provider's existing string handling stayed untouched and each adds exactly one `isinstance(val, list)` branch (see `get_page`'s contract in `providers/base.py`). A `str` is the free-text path; a `list` is the picker path for an enum-like column (`Column.options`), an OR of exact matches whose entries may be the `FILTER_EMPTY`/`FILTER_NOT_EMPTY` sentinels. Those sentinels are `"\x00"`-prefixed rather than reusing the typed `"empty"`/`"not empty"` keywords because a real option could legitimately be named "empty". An empty list never reaches a provider — `action_filter_column` drops the key instead, which is why its callback tests `if not val` rather than `if val == ""`. Still session-only state, unlike sort: nothing persists it to `ViewSettingsStore`.
### Virtual tables (`virtual_table.py`)
- dbman's premise is that everything is a table, so things that aren't database rows — an enum column's option set, and later a column's own display settings — get the same vocabulary (row cursor, `j`/`k`, a filter, an opener on the selected row) rather than a bespoke widget each. `VirtualTable` is the seam: `columns()`, `rows()`, and optionally `open_row(key)`/`clear()`/`result()`. `VirtualTableScreen` renders one modally.
- **Deliberately not built on the `Provider` ABC.** A `Provider` is ~25 methods of schema reflection, cursor paging, capabilities and write paths; a list of 18 Notion options needs none of it, and making every virtual table implement that surface would be a tax with no payer.
- The **opener** is `space`, following `PLANNING_space-vs-edit-keybinding.md`'s split of `space` ("see it more truly") from `e` ("change it"). What opening *means* belongs to the table — for `OptionPickerTable` it toggles the row's tick, which is why `open_row` returns whether anything changed and the screen re-renders on `True`.
- `OptionPickerTable` serves both arities from one class: in single mode toggling a row clears the others, so editing a `select`/`status`, editing a `multi_select`, and filtering any of them are the same screen. Re-picking an already-picked option in single mode clears it. A `Value` column appears only when some option's value differs from its name (a relational FK lookup's `(display, key)` pairs) — for Notion the name *is* the value, and a column repeating `Name` on every row is noise.
- **Selections live in the table, not the widget.** That's what makes filtering safe: narrowing the list to `auth*` can't drop a tick made under `13`. A widget-owned selection (Textual's `SelectionList.selected` only reports options currently present) silently would — which is the concrete reason this seam exists rather than a `SelectionList` with a search box bolted on.
- The picker's search box is **looser than the main table's text filter**: the term is matched as a fragment with `*`/`?` as wildcards inside it (implicitly `*term*`), so `13` and `auth*` both find `"13. Auth & Collaboration"`. The `f`-on-a-text-column box stays a whole-string glob, because it builds a stored query over rows the app may never have seen; this one narrows a short list already on screen, where forcing someone to anchor a search they can see the results of is just friction.
- **Never name a method `_render` on a Textual widget or screen.** `Widget._render()` is Textual's own internal "turn `render()` into a Visual" hook; shadowing it makes the whole screen render as `None`, surfacing a long way from the cause as `AttributeError: 'NoneType' object has no attribute 'render_strips'` deep inside the styles cache. `VirtualTableScreen._populate` is named the way it is for this reason.

- `action_edit_cell` is polymorphic on `Column.options`: an enum-like column gets an `OptionPickerTable` (see "Virtual tables" above), everything else keeps the free-text `Input`. `action_filter_column` makes the same fork before pushing a screen at all — `FilterColumnScreen` is text-only, and an options column goes to the picker instead, with `FILTER_EMPTY`/`FILTER_NOT_EMPTY` appended as two pseudo-options. The edit path also refuses `read_only` columns up front. Note `perform_choice_update` deliberately skips the `str`→`int`/`float` coercion that the free-text `perform_update` applies — an option is a name, even one that looks numeric.
- **Rebuilding the sidebar is asynchronous, and the rest of the app has to respect that** (`refresh_sidebar` → `_rebuild_sidebar`, an exclusive worker). `ListView.clear()` removes its children via an awaited `AwaitRemove` while `append()` lands synchronously, so repopulating without awaiting leaves the widget holding the *previous* contents followed by the new ones — and since assigning `.index` emits `Highlighted`, which `on_list_view_highlighted` turns into a `load_item`, resolving a row position against that transient list doesn't just mis-highlight, it loads the wrong item. Two crashes came from the earlier scan-the-children version, both on connection switch (`c`): an index past the end of the settled list, so the next `up`/`k` raised `IndexError` out of `ListView.action_cursor_up`; and an index landing on a *stale* row, loading an item from the connection being left, which the new provider has never heard of (`KeyError` out of `NotionProvider.get_schema`). It looked correct for a same-content refresh (`m`-cycling) only because the stale half is identical to the new one, so any offset into it coincidentally names the right item. Three things hold it together now, and all three are needed: `self._sidebar_rows` records the row order *as the rows are appended* so a position is never scanned back out of the widget; `_sidebar_rebuilding` suppresses `Highlighted` for the duration (every load that legitimately happens during a rebuild is an explicit `load_item` call), and is raised **synchronously in `refresh_sidebar`**, not inside the coroutine, or an event queued against the outgoing contents slips through the gap before the worker starts; and it's guarded by a `_sidebar_rebuild_id` generation token rather than a bare bool, because the worker is exclusive and a superseded rebuild still runs its `finally`. Anything new that needs a settled sidebar belongs inside `_rebuild_sidebar`, after its awaited `clear()`.
- Keybindings are declared as class-level `BINDINGS` lists (see `DbMan.BINDINGS` and the in-app `?`/`ctrl+p` shortcuts panel in `ShortcutsScreen` — **keep these two in sync** when adding/changing a binding).
- `V` opens `VersionScreen` (issue #13), a small modal "about" splash: a block-letter ASCII "DBMAN" banner (`DBMAN_BANNER`), the tagline, `__version__` (a plain module-level string in `dbman.py`, bumped by hand — there's no automated release/tagging process), and the repo link. Deliberately scoped down from issue #13's full superhero-mascot concept to a plain text banner: hand-drawing a recognizable figure in ASCII without visual iteration is a much bigger, more failure-prone undertaking than a banner. `--version` on the CLI (`argparse`'s built-in `action="version"`) prints the same version string non-interactively. Closes via `Escape` or the Close button, not by pressing `V` again — `ShortcutsScreen`'s `key_question_mark`/`key_ctrl_p` pattern (a screen-local `key_<name>` handler *and* an app-level `Binding` both targeting the same toggle action) turned out to double-fire when both are wired to the identical key: the modal's handler pops the screen, then the app-level binding's `action_toggle_version` (which also runs, since Textual's key dispatch and its Bindings/action system aren't mutually exclusive for the same keypress) sees an empty screen stack and immediately re-pushes it — net effect, indistinguishable from doing nothing. `VersionScreen` only wires the app-level `Binding` (for opening) and `Escape`/the button (for closing), not a matching screen-local key handler, to avoid this.
- Which of those bindings actually appear in Textual's `Footer` (and are live/dead) is context-aware, driven by `DbMan.check_action()` overriding the base no-op — Textual's built-in dynamic-actions hook, read from `Screen.active_bindings` any time `refresh_bindings()` is called. `DbMan.ACTION_CONTEXTS` maps an action name (not a key — `alt+left`/`alt+right` both resolve to `"reorder_column"`) to a predicate `(app) -> bool | None`: `True` shows it enabled, `False` hides it from the footer entirely, `None` shows it greyed out (visible but currently inert, e.g. `Z`/unhide or `F`/clear-filters when there's nothing to restore/clear). Most predicates are built with the `_ctx(modes=..., select_modes=..., item_types=..., capability=...)` factory (an AND of whichever axes are given); `_edit_cell_ctx` and `_add_ctx` are hand-written instead since `e`/`a` are genuinely polymorphic (SQL mode edits the View's SQL, the lookup plugin edits its own config, View mode's `e` behavior further forks on `self.select_mode`; `a` adds a row on a Table but creates a new View on a View — an OR of branches, not a plain AND) and don't reduce to a plain `_ctx()`. Actions with no entry in `ACTION_CONTEXTS` are always shown+enabled — this is also how `export_csv` stays reachable without cluttering the footer: its `Binding` itself sets `show=False` (a static override, independent of `check_action`) since it's always enabled wherever a table/view is selected but doesn't need footer real estate across every select-mode. Any code path that changes `self.mode`, `self.select_mode`, or `self.current_item`/`self.current_type` must call `self.refresh_bindings()` afterward (already wired into `load_item()`, `action_toggle_mode`, `action_rotate_select_mode`) or the footer will visibly lag the real state. See issue #10.
- **Optimistic local update + debounced batch persist** — a reusable pattern, first used for row reordering (`action_move_row`/`_schedule_row_order_sync`/`_sync_row_order`, `self.row_order`/`self.rendered_rows` mirroring the `DataTable`'s row sequence), worth reaching for again anywhere a user gesture repeats rapidly (arrow-key-style navigation/mutation) and each step would otherwise cost a network round trip. Every provider call in this app runs synchronously on Textual's own UI thread, so firing one per keystroke makes a fast burst of input feel frozen — the fix isn't "make the call faster," it's restructuring when the call happens:
  1. Mutate in-memory/rendered state and redraw *immediately*, with zero network call, so every keystroke feels instant.
  2. Debounce via `self.set_timer(...)`, stopping and re-arming it on every new event so it only fires once activity actually stops (`_ROW_ORDER_SYNC_DELAY`).
  3. When the timer fires, diff the settled local state against a baseline snapshotted at the start of the burst (`_touched_row_order_slice`) to find the minimal changed range, and hand that to the provider as *one* batch call — not a replay of N individual per-step calls.
  4. Run that batch call in a background thread (`self.run_worker(fn, thread=True)`), hopping back to the UI thread via `self.call_from_thread(...)` for any follow-up that touches widgets (e.g. a reconciling `load_item()` reload) — so even the eventual network cost never blocks input.
  5. Flush synchronously (skip the debounce) whenever the in-memory state is about to be torn down anyway — navigating to a different item, quitting (`_flush_row_order_sync`, called from `load_item()` and `action_quit`) — so a pending burst is never silently dropped.

  A pitfall worth remembering alongside this: prefer a real batch primitive over replaying N single-step provider calls back-to-back, even off the UI thread. A first cut of row reordering replayed one query-then-swap provider call per keystroke; tested live against a real Notion page, this broke under a fast burst — each step re-derived the moved row's neighbor from `POST /databases/{id}/query`, and that query index measurably lagged behind its own very recent writes (a couple of seconds), so a second move issued right after the first could still observe pre-first-move ordering and silently redo the same swap instead of progressing. The fix was `NotionProvider.reorder_rows`: read every touched row's current value with point `GET /pages/{id}` calls (immediately read-your-writes consistent, unlike the query endpoint) and reassign those already-known values as a pure permutation in one pass — a backend's query/index layer can be eventually consistent even when its point reads/writes aren't, and a tight loop of read-modify-write steps can race against that lag in a way a single isolated call never would.

### Diagram mode (`DiagramView`)
- Only meaningful for providers with `capabilities.diagram = True` (currently just `SqlAlchemyProvider`); `DiagramView` is constructed with the `provider`, not a raw engine, and calls `provider.get_diagram_model()` to get nodes/edges.
- Renders tables as absolutely-positioned `TableDiagram` widgets (one `Panel` each) over a background `Static` containing hand-drawn orthogonal connector lines (`draw_lines`, using box-drawing characters directly on a character grid — not a Textual layout).
- Initial layout for never-before-positioned tables uses `layout_graph`: a simple radial placement (not true force-directed simulation — that experiment lives only in `test_layout.py` and was not ported in). Positions are persisted per-table to `_dbman_layout`, reached via `provider.sqlalchemy_engine()` — this SQL-specific detail lives in `DiagramView` rather than the `Provider` ABC since no other provider currently supports diagram mode; revisit if that changes.
- Diagram mode hides the sidebar entirely (`sidebar.display = False`) since it needs the full screen.

### Plugins (`plugins/lookup.py`)
- `LookupPlugin` is the only plugin; it appears as a synthetic sidebar entry (item_type `"plugin"`) rather than a real table/view. It auto-detects FK relationships via `inspector.get_foreign_keys()` and lets the user configure a "display column" from the related table (stored in `_dbman_lookup_config`), which then renders as a `Select` dropdown instead of a free-text `Input` when editing a matching cell in `action_edit_cell`.
- It's inherently relational, so it's only ever instantiated when `provider.capabilities.lookup_plugin` is `True`: `DbMan.__init__` sets `self.lookup_plugin = LookupPlugin(provider.sqlalchemy_engine()) if provider.capabilities.lookup_plugin else None`, and every call site (`refresh_sidebar`'s plugin list, `action_edit_cell`'s plugin branch, `action_toggle_mode`) guards on `self.lookup_plugin is not None` first.
- There's no formal plugin interface/registry — adding a new plugin currently means importing it directly in `dbman.py` and hardcoding it into `refresh_sidebar()`'s `plugins = [...]` list and the `item_type == "plugin"` branches in `load_item()` / `action_edit_cell()`.

### View settings (`view_settings.py`)
- Per-table/per-view display preferences (hidden columns, explicit widths, column order) persist to a local, provider-agnostic file: `<cwd>/.dbman/<db-name>.json`, gitignored since it's local machine state rather than shared config. `<db-name>` comes from `derive_db_name()` (last URL path segment, extension stripped) — works uniformly across bare sqlite paths, `sqlite://`/`postgresql://`/`mysql://` URLs, and `couchdb://` URLs, so it lives outside `providers/` rather than inside any one provider.
- `DbMan.__init__` builds one `ViewSettingsStore` per connection (`self.view_settings`). `load_item`'s `"view"` mode branch calls `apply_view_settings(page.columns, page.rows, view_settings)` to project the fetched `RowPage` through hidden/order before rendering, and passes `view_settings.widths.get(col.name)` to `DataTable.add_column` — this applies uniformly across providers since it operates on the already-fetched column/row list, not provider internals.

### Cell styling (`cell_render.py`)
- The render chain in `load_item` is ordered `apply_view_settings` → `compute_column_widths` → `truncate_rows` → `stylize_row`, and **that order is load-bearing**. Width math and truncation operate on plain strings; `stylize_row` runs last and wraps a cell in a Rich `Text`, which is the only thing `DataTable` cells have ever held besides raw values. Styling earlier would either get sliced mid-markup by `truncate_display_value` or (as a `Text`, which isn't a `str`) skip truncation entirely.
- `stylize_row` takes both the truncated row and the *untruncated* one, matching option names against the latter and applying the style to the former — so a long option like Notion's `"P2 — Friction / should fix before launch"` still renders in its color as `"P2 — Friction..."`. A cell is styled only when its untruncated value equals exactly one option name, which is also what makes multi-valued columns behave: a `multi_select` holding one option gets that option's color, one holding several renders as the plain comma-joined string (the join has already been truncated by then, so per-chip coloring isn't reliably recoverable).
- `OPTION_STYLES` maps the provider's own palette names to Rich styles. Four of Notion's ten (`brown`, `orange`, `purple`, `pink`) aren't Rich color names at all, hence an explicit map rather than passing the color through; an unrecognized color renders unstyled rather than raising, so a new Notion color can't break a page load. `Column.options` deliberately carries the provider's untranslated color name — mapping it to a terminal style is the UI's job.
- In-app UI now covers all three: `w` sets/clears a width override (`action_set_column_width`), `H`/`L` in column select mode reorders (`action_reorder_column`, see below), and `z`/`Z` hide/unhide a column (`action_hide_column`/`action_unhide_column`, issue #2). `z`, `w`, `f` (filter), and `Z` (via `UnhideColumnScreen`, a `Select`-based picker) are all column-select-mode-scoped — column-granularity actions only make sense once a column is the thing selected, consistent with issue #10's context system. `z`/`Z` (hide/unhide) and `f`/`F` (filter/clear-filters) are deliberately shifted-key do/undo pairs, both halves column-select-mode-scoped; the "undo" half of each greys out rather than hides when there's nothing to undo (`Z` via `_unhide_column_ctx` when no columns are hidden, `F` via `_clear_filters_ctx` when `self.filters` is empty). `action_hide_column` refuses to hide a table/view's last remaining visible column.

### Workspace (`workspace.py`)
- A flat `<cwd>/dbman.json` (not a directory — unlike `.dbman/`) holds the project-level connection registry: a `connections` dict keyed by a short name (derived via `view_settings.derive_db_name()`, reused rather than duplicated) mapping to `{url, session}`, plus a top-level `last_connection`. Gitignored, since a Postgres/CouchDB `url` can embed credentials.
- `WorkspaceStore.resolve(arg, name_override=None)` turns the CLI arg (or `None`, for a bare `dbman`) into a `(url, name)` pair without touching disk: `None` picks `last_connection` (or the sole connection); an `arg` matching an existing connection name reuses its stored `url` (and `name_override` is ignored — renaming an existing entry is a different operation than this); anything else is treated as a url/path exactly like before, with a name — `name_override` if given, else `derive_db_name(arg)` — disambiguated with a `-2`, `-3`, ... suffix on a collision against a *different* url, for saving. The actual disk write happens once connection succeeds: `DbMan.__init__` calls `workspace.upsert_connection(name, db_url)` right after `create_provider()` succeeds, mirroring how `ViewSettingsStore` needs no separate "init" step.
- `dbman.py`'s `__main__` parses args with `argparse` (`_build_arg_parser`): a positional `connection` (url/path/saved-name, optional — omitted means bare reconnect) and `-n`/`--name`, which flows straight into `resolve()`'s `name_override`. This exists because `derive_db_name` (used when no override is given) pulls the name from the connection string's last path segment, which is meaningless for some providers — e.g. a `notion://` url's page id is a raw UUID — so `--name notion` is how you get a memorable `./dbman notion` reconnect instead of `./dbman 3a502ac1-58c9-...`. `DbMan.__init__` also prefers `self.workspace_name` over `derive_db_name(db_url)` when building `ViewSettingsStore`, so the friendly name applies to the `.dbman/<name>.json` settings file too, not just the `dbman.json` connection entry.
- Session restore (last item/mode/select_mode/cursor) is best-effort and asymmetric in when it reads vs. writes: `refresh_sidebar()`'s `_restore_workspace_session()` reads it once, the first time the sidebar populates with no `current_item` yet, and falls through to the existing default-first-item behavior if the saved item no longer exists (renamed/dropped table) — same defensive posture as `load_item`'s existing same-item `saved_coord` restore. Writing happens once, from an overridden `action_quit` (the only bound quit key, `q`) calling `_save_workspace_session()` — not on every navigation, so an abrupt exit (crash, ctrl+c) loses the latest position, consistent with the app's existing crash-log-and-move-on posture (see "Notes" below).

## Testing the CouchDB provider

There's no fixture/CI setup for this — spin up a throwaway local CouchDB in Docker, on a port that won't collide with any other CouchDB container you might already have running:

```bash
docker run -d --name dbman-couch -p 5985:5984 \
  -e COUCHDB_USER=admin -e COUCHDB_PASSWORD=admin couchdb:latest
curl -u admin:admin -X PUT http://localhost:5985/plants
curl -u admin:admin -X POST http://localhost:5985/plants -H "Content-Type: application/json" \
  -d '{"name":"Tomato","color":"red"}'
curl -u admin:admin -X PUT http://localhost:5985/plants/_design/by_name \
  -d '{"views":{"all":{"map":"function(doc){ emit(doc.name, doc.color); }"}}}'
./dbman couchdb://admin:admin@localhost:5985/plants
```

Seed a mix of flat and nested/heterogeneous documents to exercise column inference and the whole-document JSON editor (`E`, or plain `e` on a `dict`/`list` cell).

## Testing the Notion provider

There's no fixture setup for this either — it needs a real Notion integration and a real page:

1. Create an internal integration at https://www.notion.so/my-integrations and copy its secret (`ntn_...` or `secret_...`).
2. Open the target Notion page in the browser, use "..." → "Connections" → add the integration, so it can see the page and its child databases.
3. Copy the page ID from the page's URL (the trailing 32-char hex string, with or without dashes).
4. `./dbman notion://<token>@notion.so/<page-id>`

Seed at least one database with a mix of editable property types (`title`, `select`, `checkbox`, `date`, ...) and at least one read-only type (`relation`, `multi_select`, or `formula`) to exercise both `_write_property` and the read-only error path.
